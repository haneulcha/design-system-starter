## 목적

사이클 3~3.2는 조작(앵커 정밀도, 목업의 정보량, 후보 UI)을 다듬었고 화면 골격은
사이클 3의 초기 배치 그대로다. 실제로 써 보면 두 가지가 남는다.

1. **화면의 순서가 형태로 안 읽힌다.** 이 도구의 1차 작업은 생성이다 — 앵커를 넣고
   4개 파일을 받는다. 조율·검증은 2차다. 그런데 지금 화면은 18px 제목 하나에 12px
   회색 라벨들이 평평하게 이어져, 앵커→팔레트→받기라는 흐름이 위계로 드러나지
   않는다. 상태색 4종은 `<details>`에 접혀 있어(`ColorPalettePage.tsx:92-109`)
   첫 방문자가 안 열면 사이클 3 D7이 막으려던 바로 그 상황 — "받아간 파일에 모르는
   색이 들어있게 된다"(같은 스펙 :367) — 이 된다.
2. **화면 크롬이 이 프로젝트 자신의 답을 하나도 안 먹는다.** 타이포는 `text-lg` ·
   `text-[9px]` · `text-[11px]` 같은 손값이고, 간격·radius·그림자도 전부 Tailwind
   기본값이다. `src/schema/`에 typography·spacing·radius·elevation v1이 있는데
   그 답이 이 화면에는 없다. "스타터가 답을 내포한다"(IDENTITY 역할 2)가 이
   화면에서는 문서에만 있는 주장이다.

### 성공 기준

1. 1440×900 뷰포트에서 앵커 입력 → 4파일 다운로드까지 **스크롤 없이** 끝난다 —
   ③ 받기 블록 전체가 첫 화면에 들어온다 (구현 후 실측으로 확인, D3의 세로 예산).
2. 화면 크롬의 타이포·간격·radius·표면 그림자가 손값이 아니라 스키마 v1 상수에서
   **생성**된다 — `src/schema/`의 값을 바꾸면 화면이 따라 바뀐다.
3. 크롬 텍스트에 12px 미만이 없다 (목업 내부는 명시적 예외 — D4).
4. 상태색 4종이 접힘 없이 첫 화면에서 보인다 (사이클 3 D7로의 회귀).
5. 뉴트럴 선택 상태와 대비 미달 요약이 보조기술에 노출된다 (D8).

### 비-목표

- 엔진(`src/color/`) · 산출(`src/export/`) · 상태 계약(`paletteState` · `paletteUrl`)을
  건드리지 않는다.
- `OklchPicker` 내부를 건드리지 않는다 — builder · lab · inspector · color-palette
  네 화면이 공유하는 컴포넌트다. L·C·H 숫자 칸이 피커 안에 있는 배치(사이클 3.1
  D1)도 그대로다.
- Tailwind `@theme` 기본 네임스페이스(`--text-*` · `--radius-*` · `--spacing-*` ·
  `--shadow-*`)를 덮지 않는다 — `global.css`는 전 화면 공유라, 덮는 순간 "이 화면만"
  이라는 범위가 거짓이 된다 (`text-2xs`만 해도 inspector·components에 34곳).
- 도구 화면 자체의 다크모드는 범위 밖 — 크롬이 다크면 다크 프리뷰 카드가 배경에
  묻혀 대비 검사가 무의미해진다. 목업의 페이지 배경(뉴트럴 50/950)이 도구의 흰
  크롬 위에서 대비되는 것이 이 화면의 검사 조건이다.
- 조정 stop 4개 초과 확대 / 모션 추가 / 프리셋 갤러리 / 저장·공유 / 온보딩.
- ResultPage / `#lab` / `#builder`는 손대지 않는다.

## 확정된 결정

### D1. 비-색 카테고리를 도그푸딩한다 — 사이클 3.1 D3 "섞지 않는다"의 부분 개정

사이클 3.1 D3은 이렇게 적었다:

> "**주의 — 이 그림자는 산출물이 아니다.** 이 프로젝트에는 엘리베이션 카테고리
> (`src/schema/elevation.ts`)가 따로 있고 그건 사용자에게 나가는 토큰이다. 여기서
> 쓰는 그림자는 **도구 자신의 크롬**이라 그 시스템과 무관하다. 둘을 섞지 않는다."
> (`2026-08-16-…-design.md:133-135`)

**이 선언을 부분 개정한다.** IDENTITY 결정 규칙 2(판단을 바꿀 때는 근거를 기록한다)에
따라 근거와 경계를 남긴다.

**개정 근거:** IDENTITY 역할 2 — "스타터가 답을 내포한다. 이 답들이 산출물과 구조에서
읽혀야 한다." 이 프로젝트의 도구 화면이 자기 스키마의 답(typography·spacing·radius·
elevation v1)을 안 먹으면, 그 답은 `docs/research/`와 산출물 파일 안에만 존재한다.
화면이 스스로 그 답으로 지어져 있는 것이 "디폴트가 쓸 만하다"는 주장의 가장 싼
실증이다.

**새 경계선 — 무엇이 토큰이고 무엇이 커스텀으로 남는가:**

| 크롬 | 결정 | 이유 |
| --- | --- | --- |
| 카드 표면(① 앵커 카드 · ③ 받기 카드), 간격, 타이포, radius | **토큰** (`--ds-*`, D2) | 정적인 표면·리듬 — 카테고리가 답한 바로 그 영역 |
| `AdjustableScale` 스와치의 depth 어포던스 | **커스텀 유지** | 0-블러 하드섀도 + press 착지 물리는 상호작용 설계다. 36px 칩에서 블러 섀도는 안 보인다는 실측(3.1 D3)과 press 이동=깊이 대응(3.2 D4)이 근거이고, elevation 카테고리의 블러 섀도로 바꾸면 둘 다 깨진다 |
| `components/Popover` | **커스텀 유지** | 4화면 공유 크롬이라 이 화면의 범위 밖 + 위와 같은 이유 |

즉 3.1 D3에서 뒤집는 것은 "크롬 전체가 토큰 시스템과 무관하다"는 일반 명제뿐이다.
그 스펙이 실제로 방어하던 대상 — 스와치 그림자의 물리 — 는 그대로 방어된다.
`AdjustableScale.tsx:60-84`와 `Popover.tsx:3-4`의 주석은 개정 후에도 참이므로
고치지 않는다.

**주의 — `DS*` 컴포넌트는 여기 못 쓴다.** `DSCard` · `DSButton` 등은
`DesignTokens`/`DesignSystem` 인스턴스를 props로 받아 **사용자가 생성한 시스템**을
그리는 프리뷰 컴포넌트다 (`web/src/components/DSCard.tsx:5-10`). 이 화면의 "카드"는
`--ds-*` 변수를 쓰는 일반 마크업이다. 이름이 비슷해서 헷갈리기 쉬운 자리라 명시해
둔다.

### D2. 토큰 파이프라인 — vite 플러그인이 `--ds-*`를 생성한다

**네임스페이스는 `--ds-*` 별도로 확정한다.** `@theme` 블록에 넣지 않는다 — `@theme`는
Tailwind 유틸리티 네임스페이스에 매핑될 때만 의미가 있는데, 기본 네임스페이스를
덮지 않기로 했으므로(비-목표) 넣을 이유가 없다. 마크업이
`rounded-[var(--ds-radius-card)]` 같은 arbitrary value로 장황해지는 비용은
받아들인다 — 전 화면 오염보다 싸다.

**생성 경로:**

```
web/scripts/tokens-css.ts        renderTokensCss(): string  (순수 함수, 테스트 대상)
web/vite.config.ts               플러그인 등록: buildStart에서 renderTokensCss()를
                                 web/src/tokens.generated.css에 기록 (내용이 같으면
                                 안 쓴다 — 무의미한 HMR을 막는다)
web/src/global.css               @import "./tokens.generated.css";
.gitignore                       web/src/tokens.generated.css 추가 — 생성물은 커밋하지 않는다
```

`web/`에는 `tsx`가 없고 별도 predev 스크립트를 루트 패키지에 걸면 두 패키지의
스크립트가 얽힌다. vite 설정은 esbuild로 번들되므로 `../src`의 TS를 그대로 import할
수 있고, `buildStart`는 dev 서버 시작과 `vite build` 양쪽에서 돈다 — 별도 실행
단계가 없는 것이 이 구조의 값이다. vitest는 CSS를 소비하지 않으므로 파일 유무와
무관하다.

**무엇을 내보내는가 — alias·토큰·레벨·프로필만, 원 스케일은 안 내보낸다:**

| 카테고리 | 내보내는 것 | 예 |
| --- | --- | --- |
| spacing | alias 8 (`generateSpacingCategory`, density=comfortable) | `--ds-space-md: 16px` |
| radius | 이름 토큰 8 (`generateRadiusCategory`, style=standard) | `--ds-radius-card: 12px` |
| elevation | 레벨 5 (`generateElevationCategory`, shadow × subtle) | `--ds-shadow-raised: …` |
| typography | 프로필 22를 `@utility ds-type-<key>`로 + 폰트 체인 2 | `.ds-type-heading-xxs` |

원 스케일(spacing 12-stop, radius 8-stop 등)을 내보내지 않는 이유: 크롬이 소비해야
하는 단위는 의미가 붙은 이름이고, 원값까지 열어두면 크롬이 스케일에서 임의로 집어
쓰는 뒷문이 생긴다. 타이포만 유틸리티로 내보내는 이유: 타이포 프로필은 size·weight·
line-height·letter-spacing·family 다섯이 항상 묶여 다니는 물건이라 var 다섯 개를
낱개로 쓰면 묶음이 흩어진다. elevation은 `ringColor` 인자를 안 넘긴다 — style=shadow
에서는 안 쓰이고(`elevation-category.ts:141-146`), ring 스타일로 knob을 돌리는 것은
이번 범위가 아니다.

**dev 중 `src/schema/` 변경은 dev 서버 재시작이 필요하다.** 스키마 상수는 카테고리
사이클에서나 바뀌지 이 화면 작업 중에 바뀌는 물건이 아니므로, watcher를 붙이는
기계장치는 IDENTITY 규칙 1을 통과하지 못한다. 알려진 한계 3으로 남긴다.

### D3. 레이아웃 — 세로 3단 스테이지, sticky 승격 없음, 세로 예산으로 해결

① 앵커 → ② 팔레트 → ③ 받기. 번호 붙은 스테이지 제목(h2 ×3, D4의 heading.xxs).
1차 작업(생성)이 이 세 단계 그 자체이므로 화면의 형태가 곧 사용 순서가 된다.

**상태색 4종은 `<details>`에서 꺼내 ②의 세 번째 항목으로 올린다.** 이것은 재개봉이
아니라 사이클 3 D7("산출물에 무조건 들어가므로 화면에 없으면 받아간 파일에 모르는
색이 들어있게 된다. 4스트립을 얇게 노출하되 조정 UI를 붙이지 않는다",
`2026-08-15-…:365-368`)의 기록된 근거로 **되돌아가는** 수정이다. 접힌 details는
"얇게 노출"이 아니라 "노출 안 함"이었다.

**꺼내는 비용은 세로 예산으로 감당한다.** 상태색 4벌을 압축한다:

- 라벨을 띠 위가 아니라 **왼쪽 열**에 — `grid-cols-[56px_1fr]`, caption.sm.
- 띠 높이 h-9(36px) → **h-6(24px)** — `AdjustableScale`에 `compact` prop 추가.
  조정 불가라 히트 타깃이 필요 없고, D7의 "얇게"가 원래 이 뜻이다.
  `showCaptions={false}`는 유지.
- 스테이지 간 간격은 `--ds-space-lg`(24). `section`(96)은 랜딩 페이지의 리듬이지
  도구 화면의 리듬이 아니다 — alias를 쓰는 것이 도그푸딩이고, 어느 alias를 어느
  자리에 쓰는가는 화면의 판단이다.

세로 어림 (1440×900, 위에서부터):

| 블록 | 어림 px |
| --- | --- |
| 상단 패딩 32 + h1(24/1.3) + 간격 | ~87 |
| ① 제목 + 앵커 카드(피커 240 + 패딩) | ~286 |
| 간격 + ② 제목 + 액센트(띠+캡션) + 뉴트럴(띠+컨트롤) + 상태색(4×24 압축) | ~414 |
| 간격 + ③ 제목 + 받기 카드 | ~124 |
| **합** | **~911** |

900 경계에 걸린다. 구현에서 실측해 성공 기준 1이 안 나오면 조일 나사는 순서대로:
상태색 띠 h-6→h-5, 카드 패딩 md→sm, 상단 패딩 32→24. 그래도 안 들어가면 그건 이
스펙의 실패가 아니라 별도 사이클의 문제로 남긴다(알려진 한계 1).

**기각한 대안 — ③이 뷰포트 밖으로 나가면 상단에 얇은 sticky 바로 승격:**
브레인스토밍에 있었으나 리뷰에서 셋 다 확인돼 뺐다. (a) 기존 sticky 프리뷰
(`ColorPalettePage.tsx:111`, `top-8`)와 충돌 — 바가 프리뷰 상단을 덮고, Popover의
`z-20`(sticky가 만드는 스태킹 컨텍스트 때문에 명시된 값, `Popover.tsx:117-120`)과
3자 z-index 조정이 필요해진다. (b) ③을 밀어내는 세로 길이의 절반이 이 제안 자신
(details 해제 +230px, 제목 확대)이 만든 것이라, 승격은 자기가 만든 문제에 대는
패치다. (c) IntersectionObserver + `DownloadRow` 중복 렌더(산출물 생성 useMemo ×2)
라는 기계장치가 "디자인을 시작하는 데 필요한 최소"를 선명하게 하지 않는다
(IDENTITY 규칙 1). 세로 예산이 먼저고, sticky는 예산이 실패했을 때 다시 논한다.

### D4. 타이포 — 스키마 프로필 5종, 하한 12px (목업 예외)

| 자리 | 프로필 | 값 |
| --- | --- | --- |
| 페이지 제목 (h1) | `heading.sm` | 24/600 |
| 스테이지 제목 (h2 ×3) | `heading.xxs` | 16/600 |
| 설명·주 버튼(다운로드 4개) | `body.sm` | 14/400 |
| 라벨·캡션·보조 버튼(copy CSS · "기본으로" · "한 번에 고치기" · 어트랙터 칩 · 상태색 라벨 · 대비 뱃지 · 프리뷰 카드 라벨) | `caption.sm` | 12/400 |
| hex · L·C·H · stop 번호 | `code.sm` | 12/400 mono |

**10~11px는 이 화면의 크롬에서 쓰지 않는다.** 승격 명단 (전수):

- `AdjustableScale.tsx:101` 캡션 `text-[9px]` → code.sm
- `PreviewPane.tsx:114` 대비 뱃지 `text-[10px]` → caption.sm
- `ColorPalettePage.tsx:99` 상태색 라벨 `text-[10px]` → caption.sm
- `NeutralControl.tsx:31,49,63` 칩·강도·"자동으로" `text-[11px]` → caption.sm
- `DownloadRow.tsx:12,48` 버튼 `text-[11px]` → body.sm(파일 4개) / caption.sm(copy CSS)
- `PreviewPane.tsx:153,170,179` summary·고치기 버튼 `text-[10px]`/`text-[11px]` → caption.sm
- `CandidatePopover.tsx:88` "기본으로" `text-[11px]` → caption.sm

**명시적 예외 — 목업 내부(`PreviewPane.tsx`의 `Mock`)는 하한을 적용하지 않는다.**
목업은 크롬이 아니라 사용자 팔레트로 그리는 축소 UI다. 하한을 적용하면 380px 카드가
부풀어 3.1 D2가 목업을 카드 하나로 접은 이유("커지면 정작 색이 안 보인다")를
거스른다.

**12px 하한은 D5의 380px 확폭과 한 세트다.** 뱃지 최장 문구가 12px에서 ~300px인데
현행 320px 사이드바의 내부 폭(~302px)에는 안 들어가고 380px의 내부 폭(~362px)에는
들어간다. 하한만 가져가고 확폭을 버리면 뱃지가 상시 2줄이 된다 — 둘은 같이
움직인다.

**기각한 대안 — 제목을 16px로 통일해 크롬을 낮춘다:** 리뷰가 "크롬이 내용(색)과
경쟁한다"며 제안했으나 기각한다. 이 화면의 진단 자체가 "위계가 2단뿐"이고 처방이
24/16/14/12 4단이다. 제목을 16으로 내리면 스테이지 제목과 같은 크기가 되어 ①②③
3단 흐름이 형태로 읽히지 않는다 — 레이아웃 결정(D3)의 근간이 무너진다. 세로 예산은
제목이 아니라 상태색 압축(D3)에서 확보한다.

### D5. 사이드바 380px · 페이지 ~1200px · lg 미만 단일 컬럼

`max-w-5xl` → `max-w-[1200px]`, `grid-cols-[1fr_320px]` → `lg:grid-cols-[1fr_380px]`,
프리뷰 sticky 유지. 좌컬럼은 724px가 되어 스와치 칸이 ~64px — 12px 캡션(3자 ~22px)이
여유 있게 들어간다. Popover의 clamp는 영향받지 않는다 — 경계가 뷰포트가 아니라 띠
자신(`stripRef`)이고 rect를 런타임에 재는 구조라(`AdjustableScale.tsx:35,42`,
`Popover.tsx:77-83`) 컬럼 폭이 바뀌면 따라온다.

**`lg`(1024px) 미만에서는 단일 컬럼, 프리뷰가 아래로 내려간다.** 1024 뷰포트에서
2컬럼을 유지하면 좌컬럼이 548px — 칸 48px로 캡션은 들어가지만 여유가 없고, 그보다
좁아지면 깨진다. 현행(1024 고정 폭)은 좁은 창에서 그냥 깨지므로 브레이크포인트
자체는 순증이다.

**좁은 폭의 조정↔프리뷰 루프는 열화를 감수하는 것으로 명시한다** (축소 프리뷰를
만들지 않는다). 사이클 3.2 D3이 적었듯 목업은 "hover 프리뷰를 실시간으로 보는
대상이라, 가리면 이 도구의 루프를 정면으로 거스른다"(`2026-08-17-…:113-115`) —
단일 컬럼에서 프리뷰가 폴드 밑이면 루프는 끊긴 것이 맞다. 그럼에도 축소 프리뷰
(하단 sticky 미니 목업)를 안 만드는 이유: D3에서 기각한 sticky 기계장치의 뒷문
재도입이고, 이 도구의 1차 사용자는 데스크톱의 나 자신이다(IDENTITY 사용자 절).
좁은 폭은 조작 화면이 아니라 읽는 화면으로 열화된다 — 알려진 한계 2.

### D6. 스테이지 ① — 피커와 hex를 카드 하나로 (시각적 묶음만)

`AccentInput`의 현행 배치(피커 왼쪽, hex 입력 오른쪽, `AccentInput.tsx:23-24`)를
`--ds-radius-card` + `--ds-space-md` 패딩의 카드 마크업으로 감싼다. **그것뿐이다.**
L·C·H 숫자 칸은 `OklchPicker` 내부에 그대로 있다 — 사이클 3.1 D1이 근거를 남기고
정한 배치("밖으로 끌어올리면 피커의 '드래그 중에는 hex를 거치지 않는다'는 설계가
깨진다", `2026-08-16-…:62-65`)이고, 그 근거는 여전히 유효하며, 피커는 4화면
공유라 이 화면의 범위 밖이다(비-목표).

### D7. 스테이지 ③ — 받기 카드

- 카드 표면: `--ds-radius-card`(12px) + `--ds-shadow-raised` — D1 경계선 안의
  토큰 사용. 페이지에서 유일하게 그림자로 뜬 카드다. 1차 작업의 종착지가 가장
  무거운 표면인 것이 D3의 위계와 같은 말을 한다.
- 다운로드 4개 버튼은 **위계 동등 유지** — 4개 산출물이 "최소" 주장의 일부라
  (IDENTITY 비-목표) 어느 하나를 주 버튼으로 올리지 않는다. body.sm.
- **copy CSS는 회색 텍스트에서 명시적 보조 버튼으로** — 테두리 있는 caption.sm
  버튼. `canCopy()`가 false면 disabled + 인접 caption.sm 사유 문구("클립보드를 쓸
  수 없는 환경") — 현행은 opacity 40%로 죽어만 있고 이유가 없다
  (`DownloadRow.tsx:47-48`).

### D8. 접근성 묶음

1. **NeutralControl — 선택 상태를 `aria-pressed`로.** 어트랙터 칩·강도 버튼의 선택
   상태가 현재 1px 테두리 색 차이로만 표현된다(`NeutralControl.tsx:31-35,49-50`).
   각 버튼에 `aria-pressed`, 두 묶음에 `role="group"` + `aria-label`("뉴트럴 색조" /
   "강도"). **radiogroup 패턴을 쓰지 않는 이유:** APG 라디오 패턴은 roving tabindex +
   화살표 이동=선택까지 요구하는데, 화살표 이동이 곧 확정인 함정은 이 화면이
   `CandidatePopover`에서 이미 밟아 본 것이다(사이클 3.2 알려진 한계 3). 토글 버튼
   그룹은 Tab 순회 그대로라 그 함정이 없다.
   세 덩어리(색조/강도/자동으로)의 시각 라벨도 이때 같이 붙인다 — 단 라벨은
   `aria-pressed` 다음이지 대체재가 아니다.
2. **대비 미달 요약을 `role="status"`로.** 시각적으로 숨긴 요약("대비 미달 N건,
   조정 가능 M건")을 **확정 팔레트(`scales`) 기준**으로 렌더한다. 뱃지 목록 자체에
   `aria-live`를 달지 않는 이유: 뱃지는 hover 프리뷰(`shownScales`)까지 반영해
   스와치를 스칠 때마다 바뀌므로 그대로 live면 스크린리더 스팸이 된다. "hover는
   미리보기일 뿐 확정이 아니다"라는 이 화면의 기존 계약
   (`ColorPalettePage.tsx:36-39`)을 통지에도 적용하는 것이다.
3. **heading 구조:** h1(컬러 팔레트) + h2 ×3(① 앵커 / ② 팔레트 / ③ 받기). DOM
   순서 = 시각 순서 = 포커스 순서: 좌컬럼 ①→②→③ 다음 사이드바. 사이드바는
   `aside`로.
4. **프리뷰 라이트/다크 카드 라벨은 목업 바깥 크롬 영역에** — caption.sm,
   중립 텍스트. 목업 안(사용자 팔레트 배경 위)에 넣으면 크롬 중립 텍스트의 대비를
   보장할 수 없고 "크롬은 중립 고정, 팔레트는 프리뷰 안에서만"의 선도 흐려진다.

### D9. stop 50 확인 항목 — 메커니즘은 그림자가 아니라 칩↔페이지 경계

브레인스토밍은 "stop 50의 2px 그림자가 neutral-300인데 페이지 배경도 흰색이라
신호가 약하다"로 적었는데, 이 진단은 사이클 3.1이 이미 정정한 오류를 다시 밟는다:
"그림자는 칩 색과 무관하게 흰 페이지 위에 드리우므로 '옅은 칩이라 대비가 낮다'는
진단은 틀렸다"(`2026-08-16-…:171-175`). 그림자 바는 조정 가능한 4 stop에서
동일하다.

**확인할 것은 경계다:** stop 50의 거의 흰 칩이 흰 페이지에서 `border-neutral-300`
1px로만 분리되므로, 그림자 바가 depth가 아니라 "칩의 아래 테두리"로 오독되는지를
확대로 확인한다. 처방이 필요하면 칩 경계 쪽(테두리 강화 등)이지 그림자가 아니며,
"그림자 색 = 테두리 색" 규칙(`AdjustableScale.tsx:70-73`)은 유지한다.

**각주 — 3.1 문서와 현 코드의 불일치:** 3.1 알려진 한계 3의 해소책
(`hover:shadow-md` → `hover:shadow-lg`)은 사이클 3.2 D4가 hover 리프트 자체를
제거하면서 코드에서 사라졌다. 3.1의 정정된 **진단**(그림자는 칩 색과 무관)은
유효하고, **해소책** 문장만 낡았다. 3.1 문서는 역사적 기록이라 고치지 않고 여기
각주로 남긴다.
